# Публикация и сервер

## Что публикует скрипт

`deploy-site.ps1` публикует **статику** в Yandex Object Storage. Бакет не запускает Python: сам по себе он **не обеспечивает общий вход, сессии и чат**. Для них нужен постоянно работающий `server/app.py` с общей SQLite-базой.

Порядок релиза:

1. Подготовить плейлист и временные HTML. Обычный запуск скрипта вызывает `tools/generate_playlist.py` и обновляет плейлист — это не dry-run.
2. Удалить только явно перечисленные старые служебные объекты из корня бакета. Загрузить публичные ресурсы; HTML исключены из `sync` последним фильтром.
3. Загрузить CSS/JS с версией в имени, плейлист и остальные зависимости.
4. Опубликовать `yard/index.html`, затем корневой `index.html`. Любой ненулевой код AWS CLI останавливает релиз; сообщение `Done.` при ошибке не выводится.

Предыдущие версии CSS/JS остаются в бакете для уже открытых и закешированных страниц. Нет `sync --delete`, массового удаления версий или очистки локальных версионных файлов. Удаление устаревших публичных объектов — отдельная согласованная операция после проверки ссылок и срока хранения. Служебные файлы `.env`, база, исходники Python и ключи не должны публиковаться.

Это **не транзакция всего сайта**: две HTML-страницы меняются последовательно; общие ресурсы без версии перезаписываются. Ошибка между HTML-загрузками может оставить страницы разных релизов. Не запускайте публикации параллельно; текущая версия основана на времени с точностью до секунды. Для отката нужны сохранённые HTML **и** совместимые ресурсы/плейлист предыдущего релиза. Автоматического отката нет.

## Локальная проверка без публикации

Из корня репозитория на Windows с Python и PowerShell:

```text
python -m unittest discover -s tests -p test_deploy_release.py -v
```

Тесты исполняют копию настоящего PowerShell-скрипта в отдельном временном каталоге. AWS заменён регистратором вызовов, Python — заглушкой: сеть и реальные плейлисты не затрагиваются. Проверяются порядок публикации, сохранение старых ресурсов и остановка на каждой ошибке AWS. Это не проверка реального бакета, CDN, SMTP или production-сервиса.

Только после отдельного разрешения на реальную публикацию, проверки изменений и AWS-профиля запускают `powershell -NoProfile -File .\deploy-site.ps1`. Успешные mock-тесты не дают такого разрешения.

## Общий вход и чат: требования к production

Схема: браузер → **HTTPS reverse proxy на домене сайта** → Python на `127.0.0.1:8080`. Маршруты `/api/*` должны идти в Python на том же origin, без удаления префикса `/api`. Статика может идти через тот же proxy из object storage либо из Python; это требует отдельной настройки инфраструктуры, которой скрипт публикации не делает.

- Не выставляйте встроенный Python HTTP-сервер напрямую в Интернет. Ограничьте доступ к backend-port прокси-сервером.
- Прокси должен сам выставлять `X-Forwarded-Proto: https` и корректный `X-Forwarded-For`, заменяя недоверенные входящие значения. Текущий сервер использует их для `Secure` cookie и ограничения запросов. `/api/*` нельзя кешировать; сохраняйте `Cookie` и `Set-Cookie`.
- Для `/media/*` нужна поддержка byte ranges: пропускать `Range`, сохранять `206`, `Content-Range`, `Content-Length`, `Accept-Ranges` и корректный `416`. Не заменяйте range-ответ обычным HTML fallback. У Python есть обработчик диапазонов; поведение выбранного proxy/CDN нужно проверить отдельно, включая перемотку FLAC.
- Храните `server/data/inteonmteca.db` на постоянном диске с резервным копированием. В текущем CLI нет переменной окружения для пути базы. Копирование сайта в новый каталог без базы не переносит пользователей, сессии и чат.

### Явные параметры текущего `server/app.py`

В production задайте явно:

```dotenv
INTEONMTECA_HOST=127.0.0.1
INTEONMTECA_PORT=8080
INTEONMTECA_DEV=0
INTEONMTECA_DIRECT_CODE=0
INTEONMTECA_TRUSTED_PROXIES=127.0.0.1
SMTP_PORT=587
SMTP_STARTTLS=1
```

`INTEONMTECA_TRUSTED_PROXIES` — список точных IP доверенных proxy-peer через запятую, не CIDR. Значение `127.0.0.1` подходит только для прокси на том же хосте с IPv4 loopback-подключением; для другой топологии укажите фактический адрес. Без явно доверенного peer сервер не использует `X-Forwarded-For` для определения клиента.

Также задайте действительные `SMTP_HOST`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM` через защищённое окружение или непубличный `.env` — без секретов в Git. Сервер читает сначала `server/.env`, затем корневой `.env`; уже заданное окружение имеет приоритет. `INTEONMTECA_QUIET=1` отключает журнал запросов и не является обязательной production-настройкой.

Не включайте `INTEONMTECA_DEV=1` или `INTEONMTECA_DIRECT_CODE=1`: это разрешает возврат кода входа клиенту, а не подтверждение доступа к почте. При выключенных режимах без SMTP вход должен возвращать ошибку доступности, а не выдавать код.

Перед открытием доступа отдельно проверьте доставку SMTP, отсутствие кода в ответе API, защищённую cookie, общий чат в двух браузерах и перемотку медиа. Конфигурации системной службы, reverse proxy и TLS здесь **не развёрнуты и не проверены**; документ описывает требования, а не готовый протестированный production-деплой.
