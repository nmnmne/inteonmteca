# Inteonmteca — единый бриф на проверку и доводку

Документ объединяет мои требования из текущего запроса, контекст работы в чате «Ускорить сайт и снизить его вес» и результаты уже проведённой диагностики. Это не рекламное описание и не список идей: каждый пункт ниже должен быть проверен в браузере, исправлен при несоответствии и подтверждён тестом или измерением.

Связанный рабочий чат: @session:default/20261026_135836_7e2151

## 1. Что должно получиться

Сайт должен выглядеть цельно и работать быстро на телефоне, планшете, горизонтальном мобильном экране и десктопе.

Главные требования:

- меню **Debug**, тема и вход, а также все панели, которые они открывают, должны хорошо выглядеть на разных размерах;
- элементы должны адаптироваться по масштабу, не обрезаться, не вылезать за экран и не перекрывать друг друга;
- все меню должны иметь единое поведение: понятный активный слой, закрытие соседней панели, Escape, корректный фокус и доступные touch-targets;
- мобильные плитки плейлиста должны иметь нормальный читаемый размер; нельзя гнаться за количеством строк ценой обрезанных названий и исполнителей;
- плейлист на мобильном должен быть красиво и правильно размещён относительно чата, плеера, шапки и нижних элементов;
- сайт должен быстро стартовать даже на медленном интернете;
- сначала должны загружаться маленькие/низкокачественные текстуры и обложки, затем постепенно заменяться качественными;
- переход «сначала слегка пиксельно, затем качественно» должен быть намеренным визуальным эффектом, а не случайной задержкой или скачком;
- все скрипты нужно перебрать: убрать лишнюю постоянную работу, дублирование и конкурирующие циклы, но не уничтожить живые буквенные и визуальные эффекты;
- настройки, которые ухудшают стабильность, должны быть явно подсвечены отдельным списком с решением: оставить, изменить или удалить.

## 2. Приоритеты пользователя

1. Надёжная адаптивная компоновка и отсутствие перекрытий.
2. Быстрый первый визуальный результат.
3. Читаемый и красивый мобильный плейлист.
4. Живые буквы и атмосферные эффекты остаются, но не должны блокировать интерфейс.
5. Качественные текстуры догружаются поэтапно после запуска.
6. Никаких необоснованных отключений эффектов только ради цифры FPS.

## 3. Обязательные размеры для проверки

Проверять холодную загрузку и открытие/закрытие всех панелей минимум здесь:

- 320×568 — короткий мобильный портрет;
- 390×844 — типичный мобильный портрет;
- 844×390 — мобильный landscape;
- 768×1024 — планшетный портрет;
- 1280×650 — компактный десктоп/ноутбук;
- 1440×900 — обычный десктоп.

Отдельно прогнать DPR 1, 2 и 3 для обложек и текстур. Проверять не только скриншот, но и реальные bounding boxes, overflow, фокус, запросы сети, decoded dimensions и ошибки консоли.

## 4. Debug, тема и вход: что конкретно проверить и доделать

### Общая система панелей

- Сделать один общий responsive/popup coordinator или эквивалентную единую политику.
- Одновременно открыта только нужная панель; открытие Debug закрывает/сворачивает конфликтующие theme/auth-панели и наоборот.
- Открытая панель не должна уходить за viewport, под плеер или под другой слой.
- У всех панелей должны быть предсказуемые `z-index`, а не разные значения, зависящие от ширины.
- Escape закрывает активную панель и возвращает фокус на кнопку-триггер.
- Tab не должен уходить в скрытую панель.
- Нажатие вне панели закрывает её только там, где это уже соответствует текущему UX.
- Все кнопки на телефоне — минимум 40–44 CSS px по активной области; не допускать позднего CSS-правила, уменьшающего их до 26 px.
- Текст, ползунки, переключатели и кнопки не должны клипповаться при увеличенном системном шрифте.

### Debug

- Проверить позиционирование панели на всех шести размерах.
- Убрать фиксированную схему вертикальных позиций, которая перекрывает плейлист примерно на 82 px на мобильном.
- Debug по умолчанию выключен для посетителя на каждом входе, reload и возврате назад; ручное включение в текущем визите оставить.
- Не восстанавливать включённый Debug из `localStorage`, если это не будет отдельно согласовано.
- На мобильном Debug не должен создавать тяжёлую постоянную работу, пока панель закрыта.
- Если Debug остаётся в production, его `syncQuality` и DOM-обновления должны быть event-driven или приостановлены в скрытом состоянии.
- Проверить доступность мобильных эффектов Scatter/Dissolve/Recursion в Debug: UI не должен помечать нужные эффекты только как desktop-only.

### Тема и вход

- Триггеры темы и входа должны находиться внутри общей панели управления, а не уезжать за пределы toolbar на landscape.
- Панели должны иметь ограниченную ширину по компоненту: планшет не должен получать панель шириной почти во весь viewport (зафиксировано около 748 px при ширине 768).
- Проверить, что theme/auth-панели не перекрывают Debug и не оказываются под ним из-за разницы `z-index: 40/61/70`.
- Инициализировать тяжёлые контролы темы по открытию либо убедиться, что скрытый вариант не держит лишние MutationObserver.
- Сохранить выбранный UX темы, не менять визуальный стиль без отдельного согласования.

## 5. Мобильный плейлист и плитки

- Сначала исправить порядок первичной инициализации: после расчёта высоты shell и количества слотов должен гарантированно запускаться refit каталога.
- Не полагаться на то, что изменение только `--catalog-slots` вызовет `ResizeObserver`.
- На cold reload не должно быть скачка: ранее наблюдалась последовательность примерно 74 px → 68 px → поздний refit, что визуально дёргает плейлист.
- Расчёт слотов вести от реальной минимальной высоты строки: заголовок + исполнитель + padding + border + usable touch area.
- Не фиксировать 10–12 слотов любой ценой. Для короткого портрета и landscape лучше показать меньше полноценных плиток, чем много сломанных.
- Проверить минимум: 320×568, 390×844 и 844×390; для каждой точки подтвердить, что текст не накладывается и не обрезается.
- При возврате из mobile в desktop восстановить desktop-значения слотов и размеров.
- Сверить collapsed chat с плейлистом: чат на мобильном стартует свёрнутым тонкой полосой, а высота отдаётся плейлисту; открытие чата возвращает читаемые пропорции.
- Состояние чата не нужно сохранять между входами, если это отдельно не решено.
- Свёрнутый чат не должен продолжать обычный polling и скрытую диагностическую работу.
- Проверить нижний статус медиа: статус, длительность, volume и другие controls не должны пересекаться или превращаться в `0:00media`.

## 6. Быстрый старт и поэтапные текстуры

Реализовать двухступенчатую или многоступенчатую загрузку:

1. **Первый кадр:** минимальный CSS/DOM и маленькие текстуры/обложки, достаточные для композиции.
2. **После первого отображения:** подмена на более качественные версии только для видимых или почти видимых элементов.
3. **Далее:** фоновая догрузка остальных качественных ресурсов с ограничением параллелизма.
4. **При нехватке сети/CPU:** сохранять низкое качество дольше, не блокировать интерфейс и не запускать все большие запросы одновременно.

Требования к реализации:

- Низкое качество должно быть реальным маленьким файлом, а не большим WebP, уменьшенным через CSS.
- Кандидат выбирается по размеру элемента × DPR; не грузить 500–960 px для обложки, которая отображается примерно в 8–20 CSS px.
- Для обложек использовать rendition-кандидаты порядка 16/24/32/48/64 px или эквивалентный обоснованный набор.
- `srcset`, `sizes`, preload и ротация следующей обложки должны использовать тот же маленький подход.
- Скрытая копия активного плеера не должна заранее качать большой файл.
- Near-viewport observer может назначать `src`, но факт реального просмотра нужно считать отдельным zero-margin observer.
- Файлы должны быть content-hashed/versioned и иметь долгий immutable cache; HTML, manifests и scripts — отдельную политику обновления.
- После появления качественной версии проверить отсутствие резкого layout shift, мигания, чёрного фона и скачка цвета.
- Зафиксировать эффект визуально: стартовая пикселизация должна быть аккуратной и быстро уходить, а не выглядеть как ошибка.

Из проведённой диагностики: текущая система создавала 960×960 WebP для отображения около 7.7–19.5 CSS px; только 54 уникальных обложки занимали около 8.85 MB, а суммарный первый загрузочный вес доходил примерно до 3–5 MB и выше в зависимости от ротации. Это нужно проверять повторно после интеграции.

## 7. Анимации и приоритеты производительности

Сохранить живой характер сайта, но ввести явный приоритет:

1. ввод, кнопки, меню, аудио и foreground-буквы;
2. основной плейлист и видимые обложки;
3. активный визуальный эффект логотипа;
4. декоративные поля, дальние резиденты, невидимые копии и фоновые polling-задачи.

Проверить и при необходимости исправить:

- `text-waves.js`: не сканировать сотни невидимых glyph-узлов каждый RAF; качество должно ограничивать объём работы, но не превращать буквы в неподвижную картинку;
- три копии каталога не должны умножать DOM, observers и запросы для невидимых циклов;
- `room-resident.js`: не пересчитывать геометрию каждые 240 ms без изменения layout;
- `energy-field.js`, atmosphere и прочие декоративные RAF не должны конкурировать с буквами при нагрузке;
- `graphics-quality.js`: начинать мобильный режим с консервативного уровня и реагировать на реальную authored-work нагрузку, включая текст, каталог и polling, а не только canvas;
- `home-effects.js`: проверить разделение wall-clock длительности эффекта и ambient freeze. Текущая схема 5 s motion + 5 s freeze визуально удваивала длительность эффектов;
- мобильный scheduler эффектов должен поддерживать Scatter/Dissolve/Recursion в согласованном весе, например 5:5:1; Recursion примерно в 5 раз реже, одна сцена одновременно, корректный claim/release и восстановление после visibility change;
- alternate-logo не должен случайно занимать общий слот и задерживать пользовательские эффекты; его место в мобильной ротации нужно явно решить;
- polling чата останавливать в collapsed/hidden состоянии и возобновлять при раскрытии;
- скрытые Debug/theme-контролы не должны постоянно обновлять DOM.

Проверка производительности должна включать обычный режим и CPU throttle 4×/6×. Не объявлять физический FPS телефона по результатам одной эмуляции.

## 8. Настройки и текущие риски, которые нужно решить

### Подсветить и принять решение

- `Cache-Control: no-store` для статических обложек: ухудшает повторную загрузку. Для hashed renditions нужен `public, max-age=31536000, immutable`.
- Deploy sync без `--delete`: старые rendition-файлы могут оставаться на сервере. Нужна безопасная стратегия очистки или вечные versioned names.
- Все 26 production JS сейчас parser-loaded на главной: проверить, что реально должно быть defer/lazy/on-demand.
- Ambient clock 5/5: может делать эффекты визуально «зависшими» и слишком долгими.
- Скрытый Debug/theme/chat: скрытие через CSS не равно остановке работы.
- Mobile desktop-breakpoint конфликт: на 844×390 одновременно активируются mobile stage и desktop-edition.
- Текущие `z-index` панелей 40/61/70 и фиксированные позиции Debug создают взаимные перекрытия.
- Разные владельцы layout-расчётов (`mobile-sections.js`, `room-finish.js`, CSS) создают race/order-dependent refit.
- Текущий collapsed-chat расчёт может увеличивать каталог до 8–12 слотов и тем самым резко увеличивать glyph/cover workload.
- Дублирование обложек в трёх циклах и eager загрузка hidden player.
- Нельзя считать успешным улучшением простое уменьшение RAF или отключение requested effects: сначала измерять, что стало легче, и что пользовательский визуальный результат сохранён.

## 9. Обязательные тесты приёмки

### Визуальные

- [ ] 320×568: Debug/theme/auth не клиппуются, touch-targets не меньше 40–44 px.
- [ ] 390×844: плитки читаемы, chat/list/player не перекрываются.
- [ ] 844×390: mobile stage и desktop-edition не конфликтуют; панели внутри toolbar/viewport.
- [ ] 768×1024: панели не растянуты на весь экран без причины.
- [ ] 1280×650 и 1440×900: desktop layout не сломан мобильными правилами.
- [ ] Открытие каждой панели, закрытие соседней, Escape, Tab/focus и повторное открытие.
- [ ] Увеличенный шрифт и длинные названия треков.
- [ ] Collapsed/expanded chat и возврат через breakpoint.

### Сеть и загрузка

- [ ] Cold reload на throttled slow 3G/4G.
- [ ] Первый полезный кадр появляется до больших текстур.
- [ ] Низкое качество реально заменяется высоким по этапам.
- [ ] Не запрашиваются 500–960 px обложки для маленьких мобильных плиток.
- [ ] Проверены transferred bytes, decoded dimensions, количество duplicate requests.
- [ ] Повторная загрузка использует cache для hashed renditions.
- [ ] Полный цикл ротации обложек не возвращает большие исходники.

### Runtime и стабильность

- [ ] Нет ошибок/необработанных Promise в консоли.
- [ ] При открытом Debug/theme/auth нет лишних конкурирующих polling/RAF.
- [ ] При collapsed chat `/api/chat` не опрашивается с обычной частотой.
- [ ] При CPU throttle буквы остаются живыми, ввод и меню не блокируются.
- [ ] Эффекты не зависают на границе ambient freeze и корректно восстанавливаются после скрытия вкладки.
- [ ] На мобильном Recursion действительно возможен, но примерно в 5 раз реже.
- [ ] Полный набор unit/source tests, `node --check`, `git diff --check`.
- [ ] Реальный browser smoke test на всех шести размерах, а не только mocked layout test.

## 10. Правило завершения

Работу считать завершённой только когда:

1. код и CSS исправлены без потери текущих пользовательских эффектов;
2. тесты проходят;
3. browser-level проверки подтверждают размеры, панели, фокус, сеть и загрузку;
4. отдельно показаны измерения до/после по весу, duplicate requests, decoded covers и CPU/long-task поведению;
5. все оставшиеся спорные настройки перечислены выше и имеют решение;
6. публикация не выполняется автоматически — сначала отдельное подтверждение.
